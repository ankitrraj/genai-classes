Testing — Q&A for the Intern

1. How should I start testing a product?

Read the requirements first, then ask: what can break, and how would we find out? Write the happy path, then the edge cases.

2. What should I test first?

What hurts the user most. Login, payment, data loss — never leave those for the last day.

3. How much should I test?

Enough to be confident, not enough to be slow. Risk drives coverage, not the clock.

4. What makes a good bug report?

Steps, expected, actual, environment, evidence. Anyone should be able to reproduce it without askingyou.

5. What if it works on my machine?

Then test where it does not. Different browser, OS, network, empty data, bad data, huge data.

6. Should I automate everything?

No. Automate what is repeated and stable. Explore by hand what is new and unclear.

7. When should I stop?

When the risk is understood and documented — not when time runs out silently. Say what you did not test.

8. What do I do with a failed test?

Check whether the test or the product is wrong. Fix the test if it lied; file a bug if the product broke.
